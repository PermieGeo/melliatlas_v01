# Current Implementation

This page describes **running code**. Planned behavior is owned by [specifications](specs/README.md).

## Application composition

- `apps/api/src/server.ts` validates environment configuration, opens a PostgreSQL pool, constructs `SourceRepository`, `ProviderConfigurationRepository`, the existing Open-Meteo and Saturn services, and the small core provider registry before injecting services into `createApp`.
- `apps/api/src/app.ts` installs request IDs, Helmet, JSON body limits, global rate limiting, readiness/liveness, public map/weather/source routes and separately restricted local operator/experimental viewport routes. It translates known errors into structured responses.
- `apps/api/src/modules/weather/openMeteo.ts` calls the fixed Open-Meteo forecast endpoint with a timeout and validates current conditions.
- `apps/api/src/modules/core/` contains an internal source-capability registry and a sequential, code-defined analysis DAG. Current weather inspection passes through the registry; the Saturn registration reads only persisted viewport-index status. No agent, recommendation job, new HTTP route, or autonomous source access is enabled by this scaffold.
- `apps/api/src/modules/sources/contracts.ts` declares validated municipal/treatment-source access policy, fetch limits, document/run and text-only notice-candidate schemas. `destinationPolicy.ts` performs strict offline approval, HTTPS host and path-prefix preflight checks. `ApprovedSourceRegistry.getApproved()` loads eligible approved municipal or treatment-source registrations; `MunicipalSourceRegistry` remains a compatibility alias. `httpFetcher.ts` implements restricted DNS/TLS/redirect handling and is called only by the operator-triggered ingestion service.
- `apps/api/src/db/` owns the pool, checksummed migration runner and public source-catalog SQL. Numbered additive migrations `001`–`015` preserve source policy history, treatment ingestion/review, request throttling, district and immutable viewport-index evidence. `providerConfiguration.ts` owns versioned reads/edits, access revocation on edit, and the pure `buildProviderRequest` function. The S3a service writes ingestion runs, immutable documents and pending observations. Legacy S3b region-scanning code remains present but is **not** wired into startup.
- `packages/contracts/src/index.ts` holds Zod schemas for coordinates, weather/provenance, catalog entries, operator Provider settings and error responses.
- `apps/web/src/App.tsx` composes the beekeeper map, attributed forecasts, visible-viewport stored notice polygons and the separate local Saturn viewport-index pilot. `apps/admin/src/App.tsx` owns provider editing, explicitly requested batches, review, preview maps, cached index history and request diagnostics.

The backend remains a single Node.js deployment. The source-attributed geospatial notice endpoint exists; full identity management and production AI-agent orchestration remain future work. The internal graph runner is only a bounded foundation. **No nightly/region-wide collection worker is started.** Local administrator settings are token-free and served only on the loopback interface; an internet-facing client needs authentication and authorization. The architecture is described in [ARCHITECTURE](ARCHITECTURE.md).

## Restricted provider retrieval (SRC-01 / S2)

`apps/api/src/modules/sources/httpFetcher.ts` implements a bounded, injectable HTTPS transport for approved registry destinations and explicitly configured manual treatment sources. It pins a publicly routable DNS answer to direct TLS, validates certificates and the socket peer, rejects unsafe redirects, and caps response size, MIME, time and retries. It is used by explicit local ingestion and the opt-in Saturn viewport pilot; normal public map reads never invoke it. The legacy regional worker uses the same transport when directly invoked but is not scheduled. Migration `005_treatment_source_approval.sql` remains historical; migration 008 permits configured treatment requests without documentary approval. Configuration edits invalidate old request cursors and review metadata.

## Provider bootstrap configuration

`apps/api/src/db/seedProvider.ts` is a manual CLI for seeding the one candidate `treatment-feed` record using an external JSON preset, not a running importer. `apps/api/src/modules/sources/providerSeed.ts` validates that preset, checks for a pristine migration placeholder and preserves custom operator changes by default. Migration `006_optional_provider_api_key.sql` adds nullable `source_catalog.api_key` and excludes credentials from future immutable policy snapshots. Explicit seeding resets review approvals; normal UI updates clear the previous provider API key to prevent reuse against a different endpoint. There is no automatic retrieval or key injection into outbound requests.

## SRC-01/S3a manual provider evidence pipeline

`apps/api/src/modules/sources/treatmentIngestion.ts` connects the configured treatment source, restricted HTTPS fetcher, immutable raw JSON in `source_documents`, run records in `ingestion_runs`, and pending `source_observations`. Migration `007` prevents duplicate record candidates per exact document version and records operator review evidence. A guarded manual fetch reads one page at a time. Technically valid structured pending polygons may appear in `GET /api/v1/notices` with `reviewStatus: pending`; verified polygons remain distinguished. Rejected, text-only and pending model-extracted observations are excluded. The administrator preview uses dashed styling for pending fields; the public `MapCanvas` renders only its validated public response. A malformed geometry is kept as text-only evidence without aborting an otherwise valid page. Legacy regional scanning is not wired into startup; no automatic source permission, unrestricted endpoint probing or risk classification is enabled.

### S3a manual operator fetch simplification (2026-11-01)

Migration 008 activates the configured `treatment-feed` for **operator-triggered** fetching. The permission-approval form, `/api/v1/operator/provider/approve` route, and mandatory documentary evidence have been removed for this treatment path. No operator token is required on the loopback-bound administrator service; the HTTPS destination is derived from the database endpoint and enforced by the restricted transport. The source policy's historical municipal review semantics and immutable migration history remain unchanged. Raw responses are persisted. Valid structured pending polygons can appear in public `/api/v1/notices` with an explicit unverified label; rejected and invalid records remain excluded. The bounded S3b regional worker is separate from manual diagnostics, and there is no synthetic spatial fallback.

## S3a.4 separate local administrator application

The administrator frontend runs on loopback port 5174 and uses the same Node.js API and PostGIS database as the beekeeper frontend (5173). Configuration `PUT` never triggers a source fetch; collection is a separate bounded action. UI strings are catalog-based in each app. S3b scan/scheduling code is retained but disabled in current server composition. Authenticated remote administrator accounts and in-app event polling are not implemented.

### SRC-01/S3b bounded scan wiring

The API server no longer starts the legacy region-wide worker. District coverage metadata (migration 011) uses one key per source, configuration revision, provider district and upstream filter identity. A new operator-only read-only endpoint reports coverage; refresh is disabled until the actual district API filter contract is verified. The existing map remains a pure PostGIS bbox reader, preferring latest seen records (200-item response cap). No client request triggers third-party traffic; legacy one-page diagnostics are not equivalent to district freshness.

### S3c.1 client-driven viewport index pilot (local only)

For offline verification only, `apps/api/src/modules/sources/providers/saturn/saturnEvidenceLinks.ts` compares already validated map-index feature IDs with already parsed polygon Feature IDs and minimal observed ACR response IDs. Its report is explicitly an ID-only investigative candidate list and cannot be used as a published map geometry join. The endpoint relationship and `UpdateMap` time semantics remain unverified; no route or network fetch invokes this helper.

`saturnCaptureInspection.ts` composes the provider-specific parsers into an offline-only report for captured direct response/request bodies. `saturnCaptureCli.ts` is a local bounded-file command, not an API endpoint. It reads a single validated query page, one polygon JSONP body with its exact callback, and optional ACR JSON bodies. `saturnAcrEvidence.ts` additionally summarizes the captured ACR date ordering, original/updated product-list sizes and publication-timestamp presence, preserving null when the relevant field is absent. Output contains IDs, hashes, structural counts and status without raw source dates, names, substances, dosage or coordinates. Report status remains `ID_ONLY_UNVERIFIED` even when IDs overlap or ACR fields are structurally valid; the CLI cannot prove capture provenance, legal access, matching zoom or treatment-time meaning. See [USAGE](USAGE.md) for input format and invocation.

The optional `--manifest` argument checks manually recorded raw-body SHA-256 digests, canonical UTC capture timestamps, expected provider endpoint URLs and ACR requested IDs via `saturnCaptureManifest.ts`. It validates the polygon request's numeric `bbox` and reports its rectangle relationship to the validated `/query` request (`identical`, `overlapping` or `disjoint`) without disclosing coordinates. Missing metadata is explicitly reported as `NOT_PROVIDED`; successfully matched metadata is marked `SELF_REPORTED_METADATA_HASH_BOUND`, while the overarching ID inspection remains unverified. `sourceProfile.ts` distinguishes these observed capture-only URLs from destinations authorized for automated retrieval. No request is made for an ACR or polygon endpoint, and geometric request overlap does not prove viewport feature coverage or identity.

The explicit Saturn viewport collector and directory refresh both delegate request auditing, source-wide throttle reservation and completion status to `apps/api/src/modules/sources/auditedSourceRequest.ts`. That shared workflow never performs provider parsing or persistence. `apps/api/src/modules/sources/providers/saturn/saturnViewportPageFetcher.ts` owns the fixed POST and validated response envelope; `SaturnViewportCollectionService` then commits the returned evidence using the existing atomic index repository. Cached reads and preflight-denied requests remain upstream-inert.

`apps/web/src/components/DistrictViewportPanel.tsx` lets the user select a verified Yartsevo fallback or a district from the explicitly fetched persisted Saturn directory, re-center/zoom the Leaflet map, select the exact viewport and `UpdateMap` date window, inspect saved pagination progress, and request exactly one new page. `apps/web/src/api/client.ts` validates requests and responses with `@melliatlas/contracts` and calls the non-operator `/api/v1/map/saturn-viewport/{status,next}` endpoint. The Saturn-owned `providers/saturn/saturnViewportClientRoutes.ts` enforces a loopback peer and the local Web origin, then delegates to `SaturnViewportCollectionService`. The module uses typed provider capability ports and retains the operator view, 20-second PostgreSQL-backed minimum gap for explicit pilot requests, destination restrictions, enablement flag and durable PostGIS checkpoint. The older regional scanner retains its separate 65-second minimum. Normal map `GET /api/v1/notices` remains read-only. The indexed centers do not establish district coverage; `/acr` details and polygon rendering remain separate future work. Do not deploy source-triggering endpoints publicly without proper authentication and abuse controls.
