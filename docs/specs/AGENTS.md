# Specification Authoring Guidance

Extends [root engineering guidance](../../AGENTS.md). [Specification index](README.md) owns the current structure and lifecycle.

- Write **normative specifications** as observable behavior: purpose, actors and journeys, scope/non-goals, requirements, failure/boundary cases and verifiable acceptance evidence. Avoid implementation recipes disguised as requirements.
- Treat specification authoring as an **iterative collaboration with the developer**, not a one-pass generation task. Present the proposed scope, user journeys and consequential requirements for review; incorporate feedback and obtain explicit developer approval of the normative specification **before treating it as ready for implementation**. Reopen review if material requirements change.
- When requirements, user experience or business logic are uncertain, investigate comparable applications, interfaces, workflows and established solutions. Use findings to propose better UI behavior or simpler domain rules, explain trade-offs and distinguish observed examples from requirements the developer has approved. Research informs the draft; it does not silently expand scope.
- Maintain a separate, linked **advisory implementation plan** for each new or materially changed sub-spec. Plans identify verified existing owners versus proposed files, ordered steps, dependencies, compatibility/migrations, recovery and independent tests. Keep plans useful, not ceremonially exhaustive.
- Treat implementation planning as **iterative architectural and technical research**. Inspect the actual code and constraints, investigate viable approaches and existing implementations (including relevant solutions in other languages), and compare meaningful alternatives for maintainability, modularity, correctness, complexity, performance, security, testing and migration cost. Do not assume the first proposed design is optimal.
- Surface consequential technology, architecture, library and algorithm choices to the developer **before committing to one approach** when trade-offs or uncertainty could materially affect the product. Record the selected option, rejected alternatives, rationale and unresolved risks at an appropriate level of detail; revise the plan after feedback and new evidence. Avoid exhaustive option searches for routine implementation details.
- Keep the plan aligned with the **developer-approved specification**. If research exposes a requirement conflict or suggests a materially different user journey, propose a specification revision for approval rather than changing normative behavior through the advisory plan.
- The umbrella describes the product and distinguishes **implemented, experimental and planned** capabilities. A selected sub-spec remains focused on its current workstream; avoid unrelated future detail.
- Keep feature identifiers, stage identifiers, requirement identifiers and test scenarios distinct. Preserve existing IDs and update [feature cross-references](feature-cross-ref.yaml) only when ownership or coverage actually changes.
- Link to authoritative architecture, contracts, tests and evidence rather than duplicating long code descriptions or historical implementation logs. Confirm that cited file paths, endpoints and behaviors exist.
- Label third-party access permissions, API semantics, geographic/scientific claims and untested assumptions as verified or provisional. Never substitute a generated example for field evidence.
- `STATE.json` tracks developer-selected work and acceptance; passing tests or completing a document does not itself advance that state. Keep the current spec, linked plan and index internally consistent.
- All specifications and plans are in English, with clear prose and concise, independently testable requirements.
