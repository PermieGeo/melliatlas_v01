# SRC-01 — Source Ingestion and Evidence Map

**Parent:** [MelliAtlas MVP](../spec-umbrella-melliatlas.md) · **Plan:** [SRC-01 implementation plan](source-ingestion-implementation-plan.md) · **State:** [STATE.json](../../STATE.json).

## 1. User outcome

A beekeeper selects an area in Smolensk Oblast and sees **actual published notices and geospatial context**, with links to their original sources, understandable dates and honest location precision. The operator can inspect ingestion status, rejected records and source access settings. The first usable slice already includes a live map and server-side Open-Meteo location inspection; this sub-spec completes the durable source pipeline and evidence layer.

> **Current delivery priority (2026-11-02): S3c — District-scoped Saturn refresh.** The previously implemented S3b whole-region scan is retained as historical behavior but is **superseded as the MVP collection strategy**. Client map reads remain database-only. The new 24-hour TTL is a target for successfully completed district coverage, not a guarantee that the external source is up to date. S3c is a specification and implementation-plan change, **not yet implemented or accepted**.

**Current treatment map policy (S3a.5):** The local administrator can fetch one bounded page from a configured structured treatment source, persist its original payload and candidates, inspect pending observations, and optionally review or reject them. Public `GET /api/v1/notices` returns valid attributed WGS84 polygons with `verified` status or `pending` status only when extracted from structured provider data; pending polygons must be visibly marked as not independently reviewed. Rejected, text-only, geometrically invalid and non-structured pending records are excluded. No background crawler, source reuse authorization, pesticide-safety verdict or scientific prediction is implied.

**Source acquisition policy (updated):** A configured structured `treatment-feed` can be retrieved one page at a time by a local administrator without a documentary source-access approval form. The request destination is strictly derived from the stored HTTPS endpoint; DNS/IP, TLS, redirect, payload, rate and timeout protections are mandatory. Public map visibility is gated by technical geometry validation and configured source provenance; operator verification is a separate explicit status. Municipal sources retain their separate reviewed-access policy. This does not claim the external service's terms have been independently verified.

## 3. API and persistent data

**Verified bootstrap:**

- `GET /health/live`, `GET /health/ready`.
- `GET /api/v1/sources` reads the configured source catalog.
- `GET /api/v1/locations/inspect?lat&lon` retrieves Open-Meteo values, WGS84 coordinate echo, forecast-model provenance and UTC times.
- `apps/api/migrations/001_source_core.sql` defines the initial source catalog, ingestion runs, source documents and spatial observation tables.

**Local administrator configuration slice:**

- `GET /api/v1/operator/provider` reads the candidate provider label, endpoint, request method/region/parameters and registry revision; `PUT /api/v1/operator/provider` accepts a complete validated configuration and `expectedRevision`, returning 409 on conflict. Both are available from the loopback-bound local administrator application without bearer tokens. The revisioned backend PUT does not fetch on its own; the S3a.4 administrator UI saves without triggering a fetch, and a distinct collection action fetches one bounded page.
- `apps/api/migrations/003_saturn_api_configuration.sql` is immutable historical bootstrap. Migration `004_provider_connection.sql` creates a provider-neutral pending `treatment-feed` configuration and disables the legacy record without removing history. The registry's existing approval gate does not grant Saturn network access; a future additive change must explicitly support reviewed treatment sources.
- `buildProviderRequest` is a pure programmatic interface accepting the endpoint and typed JSON request parameters, including nested region filters; it sends no network requests and makes no authorization decisions. `parseBeekeeperPlanPage` is a separate reference-shape parser and never claims records are verified or safe to publish.

**Planned endpoints for this stage:**

- `GET /api/v1/notices?bbox=minLon,minLat,maxLon,maxLat&from=...&to=...&cursor=...` returns **reviewed** notice summaries and geometries with bounded pagination and stable IDs.
- `GET /api/v1/notices/:id` returns the original citation, publication/update timestamps, extracted fields, geometry precision and review history visible to the authorized user.
- `GET /api/v1/sources/:id/status` returns operator-readable fetch/ingestion diagnostics, access-restriction information and last success; access control must be added before sensitive operational detail is exposed.

**Normalized notice:** `id`, `sourceDocumentId`, `sourceId`, `canonicalUrl`, `publishedAt?`, `retrievedAt`, `effectiveFrom?`, `effectiveTo?`, `locationText?`, `geometry?`, `spatialPrecision`, `crop?`, `substanceAsPublished?`, `reviewStatus`, `extractionMethod`, `sourceVersion`, `dataQualityFlags[]`. A missing `effectiveTo` or unknown geometry stays explicit. Store no inferred pesticide hazard class without a separately verified product reference.

**Persistence:** Keep raw document versions immutable; deduplicate identical `(sourceId, canonicalUrl, sha256)` downloads. A new hash is a new revision. A normalized observation references its exact document version, uses transaction-safe publication, and can be superseded without deleting history. Reserve a unique job claim/lease for worker concurrency. Geometry is indexed with GiST; notice time ranges with B-tree/GiST as measured.

## 4. Ingestion behavior

1. Source registry approves a source, access method, allowed domains, quota and parser version.
2. Scheduler leases an eligible source, records a run and fetches documents with an allowlisted client.
3. Raw payload, metadata and content hash are committed before extraction. Duplicate content is recognized without losing run evidence.
4. Deterministic HTML parsing extracts publication metadata; strict schema normalization records field-level evidence. Scanned attachments that need OCR remain pending with an explicit reason until a reviewed extractor is available.
5. Spatial normalization uses only published polygon geometry or documented place/area resolution with its precision. Ambiguous locations are `text_only`.
6. Review policy determines whether an observation is published. A pending model-extracted claim is not a verified notice.
7. The API reads a stable, paginated snapshot; the UI shows findings with original links and timestamps.

## 5. Security and data-quality boundaries

- Fetch accepts only pre-registered HTTPS hosts and explicitly approved paths. Resolve and check DNS/redirect targets, block loopback/link-local/private address ranges and cloud metadata endpoints, cap response bytes and MIME types.
- Treat source HTML/PDF as untrusted data; strip active content, do not execute embedded scripts, and do not allow document text to control fetch tools or operator configuration.
- No public endpoint triggers unbounded scraping. The administrator API is bound to localhost and rejects non-local browser origins; configuration changes require revision checks and no-store responses. For production rollout, operator authentication must be evaluated against deployment security requirements; setting a candidate URL never grants fetch permission.
- Keep secrets and private apiary positions outside raw source artifacts, model prompts and source API responses.
- Provider rate limits and terms take priority over requested polling cadence. Failed and partially successful runs remain inspectable.
- Show source coverage and quality flags; do not equate absence of a notice with absence of agricultural treatment.

### Provider configuration coverage

- **SRC-T12:** Unauthorized or missing operator credentials cannot read or mutate settings; no configured token fails closed.
- **SRC-T13:** A valid operator change persists across reads with a monotonic revision; a stale revision returns 409 and leaves the latest record intact.
- **SRC-T14:** Programmatic GET/POST request construction accepts an explicit region and bounded parameters; invalid URL, reserved/duplicate region key, malformed fields and IP-literal endpoints fail validation. Constructing a request does not fetch any data.
- **SRC-T16:** Repeated provider preset installation preserves operator edits and returns a no-op for identical settings. Explicit replacement resets approvals and API keys; database revision snapshots contain no credentials and no seed fetches a source.
- **SRC-T15 (future):** A reviewed Saturn source safely fetches, parses and retains real records with original published evidence; re-fetch and unsafe DNS/redirect attempts obey SRC-R03 and SRC-R09.

## Local administrator preview increment (2026-11-01)

- Administrator settings load without a bearer token. `PUT /api/v1/operator/provider` saves the revision; the UI immediately invokes one `POST /api/v1/operator/provider/sync` and refreshes the map. An explicit retry is available. Saving succeeds independently of later upstream errors.
- The API server binds to `127.0.0.1` and refuses cross-origin browser requests to `/api/v1/operator/*`. These controls are local-development boundaries, not production identity or internet-facing authorization. A future public client must exclude these routes.
- `GET /api/v1/operator/notices/map-preview` returns only real source-derived valid `Polygon`/`MultiPolygon` observations with status `pending` or `verified`; each has source provenance and its verification state. The preview is not a public publication or safety assessment. As of S3a.5, public `GET /api/v1/notices` additionally permits technically valid structured pending polygons with an explicit unverified status.
- A standalone one-page probe at `scripts/check-saturn-api.mjs` reports upstream HTTP/JSON status and polygon candidates without storing data, inventing coordinates or claiming source availability when the probe cannot execute.
- Acceptance: verify token-free save, one POST per save, source failure messaging, localhost-only binding and cross-origin rejection, pending/verified visual differentiation, public pending exclusion, PostGIS preview and deterministic offline script tests.

### S3a.4 — Separate beekeeper and local administrator applications

- **SRC-R-UI-01:** `apps/web` presents a map-first beekeeper interface. Treatment polygons MUST come only from `GET /api/v1/notices`; the app MUST NOT bundle operator configuration, ingestion administration, preview or review APIs. A separately gated local-only source-index pilot defined in SRC-R33 may offer an explicit one-page user action, never automatic collection from ordinary map reads. A missing map layer MUST NOT be represented as absence of spraying.
- **SRC-R-UI-02:** `apps/admin` is a separately built localhost frontend. It provides distinct configuration, collection, pending-record review and operator preview views. The existing backend remains the sole owner of source fetching and PostGIS writes; no independent admin backend or data copy is introduced.
- **SRC-R-UI-03:** Saving provider configuration MUST NOT trigger an upstream fetch. Collection is a separate explicit action; the current API contract fetches at most one bounded page per action and the UI MUST communicate that limitation, not claim a complete region refresh.
- **SRC-R-UI-04:** The backend MUST deny browser `Origin` values associated with the beekeeper app on operator routes and allow the local administrator origin; both frontend and API MUST remain loopback-only until administrator identity and server-side authorization are implemented. Origin validation alone is NOT authentication. The system MUST NOT be deployed with public operator routes in this state.
- **SRC-R-UI-05:** New beekeeper/operator controls and source-related messages MUST use localized catalogs; API error codes and scientific/source facts MUST remain language-independent. Each frontend MUST preserve meaningful loading/error/empty states.
- **SRC-R-UI-06 (future):** A bounded, resumable region-wide collection worker may scan the configured administrative region at a conservative provider-compliant rate, potentially overnight. It MUST measure coverage and progress and MUST NOT claim complete/fresh data after receiving only the first page. No 10-minute freshness guarantee or server-side alerts are implemented by this UI split.

**Acceptance scenarios:** public map calls no operator routes; administrator opens settings without collection; save issues exactly one `PUT` and no sync; an explicit collection action triggers at most one POST; pending structured valid polygons are explicitly labelled as unverified in public map responses, while other pending candidates remain administrator-only; both locales render core labels and errors; 5173 browser origin cannot trigger operator actions, 5174 is accepted on the local backend; backend and web builds remain independent. Full region collection, user accounts, polling notifications and hosted administrator login are subsequent scopes.

### S3a.5 — Public visibility of valid structured treatment plans (2026-11-02)

- **SRC-R-PUB-01:** The configured `treatment-feed` may expose valid, source-derived `Polygon`/`MultiPolygon` observations through public `GET /api/v1/notices` when their review status is `verified`, or when it is `pending` and their extraction method is `structured`. The query MUST enforce active configured source identity, original endpoint correspondence, WGS84 geometry and topology validity, the existing bounded result count, and optional bbox filtering. `rejected`, text-only, invalid geometry, and non-structured pending records MUST remain absent.
- **SRC-R-PUB-02:** Every public pending record MUST retain its original source URL, retrieval date and `reviewStatus: pending`. The beekeeper UI MUST display an explicit unverified warning and distinguish these polygons visually from `verified`; it MUST NOT claim an actual application event, an independently confirmed pesticide danger or a complete regional dataset. Missing or unknown data remains null/unknown.
- **SRC-R-PUB-03:** Operator verification and rejection remain independent actions with their existing immutable evidence audit. Neither import nor public visibility automatically records an operator approval. The public map MUST NOT call administrator endpoints or trigger upstream network traffic. Disabling/reconfiguring the provider must remove inappropriate records from public results without deleting their evidence history.
- **SRC-T-PUB-01:** A stubbed source produces one valid structured pending polygon that is visible in the public and administrator maps before review, with identical provenance and explicit pending status. Operator verification changes its label without creating a new geometry. Rejection removes it from the public result.
- **SRC-T-PUB-02:** Pending model-extracted/text-only/malformed/rejected candidates, disabled sources, mismatched source endpoint, and bboxes outside the geometry are excluded. HTTP 400 bbox and read-only provider behavior are unchanged.
- **SRC-T-PUB-03:** Both locales explain the independent-review limitation; a source-attributed pending polygon renders distinctly in desktop/mobile map tests, without revealing operator controls. Tests use synthetic evidence and never contact the real provider.

**Boundary:** This stage relaxes the individual-review publication filter only for validated structured treatment geometries. Provider reuse/publication terms still require separate operator assessment before public deployment. No migration, automatic source polling, hazard inference or new permission model is introduced. This section supersedes the older S3a/S3a.3/S3a.4 verified-only public-map acceptance wording where those conflict; historical stage descriptions remain as implementation history.

### S3b — Bounded whole-region collection (historical implementation; superseded for new MVP work, 2026-11-02)

- **SRC-R20:** The operator can start, pause and resume a server-managed scan of the single currently configured provider region. The configured provider request retains its original source filter; no beekeeper API request starts source collection. Regional scans and manual one-page collection MUST NOT run concurrently.
- **SRC-R21:** Each regional page passes through the existing restricted HTTPS fetcher and PostGIS validation. At most one page is claimed per worker tick, with at least 65 seconds between claimed starts, including after process restart; no unbounded parallel fan-out or new broker/cache is introduced. Persist the next-page cursor, count of fetched pages, received records, stored observations and reported total in `source_catalog.source_cursor`, atomically with a successfully stored page. Reject malformed or contradictory page termination and stop at 2,000 pages rather than claiming completion.
- **SRC-R22:** Progress survives backend restart. Three consecutive page failures pause collection with a sanitized code; a manual resume retries the saved page. A pause during an in-flight fetch must prevent that page's commit. Only an actually terminal page changes the status to `completed`; a page-sized response, network failure, partial run or configured-region change cannot imply full coverage.
- **SRC-R23:** With an explicitly configured UTC hour, the backend attempts one new daily scan after that hour. The hour is not country-specific; without the setting, only operator start and restart recovery run. A disabled source cannot be fetched. Schedule attempts do not bypass provider rate limits or allowlisting. A paused failed scan requires operator action rather than silent repeated high-load retries.
- **SRC-R24:** The beekeeper map requests stored polygons for its visible Leaflet bounds, never the upstream provider. The public PostGIS projection shows the latest stored revision per available upstream record ID and continues excluding rejected, invalid, unlocated and impermissible pending results. The response remains capped at 200 records per request: it is a bounded viewport result, not a complete inventory for large map extents.
- **SRC-R25:** The administrator can inspect region code, state, pagination progress, provider-reported total and sanitized errors without raw provider payloads, credentials, or private coordinates. UI strings for these controls are localized in RU/EN. Neither a reported total nor a successful scan guarantees that a changing upstream listing is a consistent snapshot or that every plan has usable geometry.

**Independent acceptance scenarios:** Two-page fixture with a stable region filter, saved progress across worker restart, manual/scan mutual exclusion, pause/resume, stable cursor after a network error, no parallel fetch on consecutive ticks, count mismatch failure, configured-hour schedule, disabled source failure, and both public/administrator API separation. Cover public latest-revision precedence and viewport geometry in a real PostGIS test, plus desktop/mobile map behavior. Only actual passed checks establish acceptance. Historical source legal/republication requirements remain separate and must be reviewed before external deployment.

### S3c — On-demand district collection and 24-hour freshness (current priority, 2026-11-02)

**Decision:** During the Smolensk Oblast pilot, the server collects only explicitly needed **administrative districts**, not every page for the whole oblast. Multiple beekeepers share a district dataset; their map circles remain PostGIS read filters, not external fetch/cache keys. A stable external district ID and any period-filter parameter must be verified against actual portal requests before enabling those selectors. **The currently configured `subject: 55` is a candidate internal portal identifier, not a verified official Smolensk region code.**

- **SRC-R26 — Verified query contract:** Record a sanitized real request/response for selecting Smolensk Oblast, one district and an application-period filter using the public portal's Network interface. Verify mapping from human-readable regions/districts to **provider** IDs, request field names and values, pagination and terminal conditions, date semantics, rate limits and automated-use/republication conditions. A UI filter alone does not prove a corresponding backend filter, `updatedSince`, individual-plan lookup or `lat/lon/radius` endpoint. Until verified, unsupported filters MUST remain disabled, never silently ignored; no automated mass fallback to an entire oblast.
- **SRC-R27 — Cache identity and freshness:** Store completion metadata in PostgreSQL for each canonical **source + configuration revision + verified district + actual upstream filter set**. Include an application-period bucket only after its exact upstream filter is verified. A cache entry is `fresh` for **24 hours** from the end of a successfully completed, bounded listing of that exact key. Store `completedAt`, `expiresAt`, coverage state, source filter identity and failure reason. A partial page, canceled job or absence of polygons never establishes fresh coverage; a fully successful **zero-result** listing may. A configuration/filter change invalidates the old coverage key without deleting evidence.
- **SRC-R28 — Read path and bounded refresh:** `apps/web` MUST read only the local, spatially filtered PostGIS map API. If requested district data is fresh, it MUST NOT trigger a provider request. For a cold or expired district, the backend MAY enqueue one rate-limited refresh for that key while returning previously stored data or an explicit incomplete state. A map request MUST NOT wait on upstream pagination, fan out to an entire region or expose operator endpoints. Concurrent requests for the same key coalesce into one job; external request limits remain enforced across different keys.
- **SRC-R29 — Explicit operator action:** The localhost administrator UI MUST offer `Refresh district now` independently from provider settings. It bypasses **freshness TTL only**, not host restrictions, provider throttling, concurrent-job guards, pagination caps or source access policy. The operator sees requested district/filter, running/partial/completed/failed state, counts, last complete refresh and sanitized failure. Do not label a first-page probe or a fetch of recent pages as a completed or changes-only refresh.
- **SRC-R30 — Coverage boundaries and errors:** A point/radius crossing district boundaries needs each intersecting district's coverage; until a verified district boundary catalog is available, the UI MUST report potentially incomplete neighboring coverage rather than infer it from a single district. A failed or stale refresh keeps the last saved attributable observations with their original timestamps and an explicit freshness warning, never a claim of no planned treatments. Preserve immutable source evidence and source-backed pending/verified/rejected publication policy.
- **SRC-R31 — Superseding whole-region scheduling:** The legacy manual/UTC-scheduled whole-region scan introduced by S3b MUST NOT remain an active competing collection mode after S3c becomes the production path. The migration must disable any `REGION_SCAN_DAILY_UTC_HOUR` deployment setting and safely reconcile or suspend existing `source_cursor.scan` state; no unfinished scan may masquerade as district coverage. Do not delete old documents, run history, or migrations.
- **SRC-R32 — Optional notification email feasibility:** A region-specific official email subscription is a **candidate auxiliary signal**, not a trusted full-data replacement. Verify at least one original `.eml` message, sender authentication evidence, stable plan IDs/links, amendment/cancellation semantics and whether the geometry/chemical fields are present **before implementing ingestion**. Never feed arbitrary email links into the network fetcher. No automatic mailbox access, credentials, mail schema or notification delivery is authorized by this stage.

- **SRC-R33 — Explicit client-initiated viewport-index pilot (2026-11-07):** Before production account authorization exists, a loopback-only beekeeper client MAY explicitly start one validated page of the observed Yartsevo (`district=1477`) `POST /query` index when the operator has enabled permitted source access. The browser must choose the district and visible bbox and date window, and require a user click for each page; navigation, initial render, passive cache inspection and status polling MUST NOT fetch. The server MUST expose a non-operator route restricted to a local browser origin and loopback peer, reuse the same configured provider, fixed HTTPS allowlist, source-wide 65-second throttle and transactionally persisted cursor, and refuse unsupported regions/ranges, disabled access and requests without an allowed origin. Loopback/origin checks are **not authentication** and MUST NOT be treated as sufficient for an internet-facing deployment; remote clients cannot initiate ingestion until a separately specified authorization and abuse-control design exists. The UI MUST label index entries as field-center summaries rather than verified treatment polygons, distinguish errors/partial/completed viewport paging, and link plainly to the local Admin instructions. No client access to `/api/v1/operator/*` is permitted.

- **SRC-R34 — Visible saved viewport-index evidence (2026-11-07):** For the local pilot, an explicit client cache read or completed one-page fetch MUST return at most 100 already stored WGS84 field-center points for the exact filter. Display them as a distinct labeled index layer, NEVER as treatment polygons, proof of spraying, or a safety verdict. Switching district/bbox/UpdateMap dates MUST clear obsolete markers and report invalid date windows (maximum 124 days), including a corrective bounded-range action. A disabled collector MAY still expose saved index evidence through read-only status, but MUST NOT start upstream traffic. Local Admin MUST show a bounded database-backed history of the latest 20 saved viewport filters and up to five latest committed page receipts per filter; every record shows district, exact filter dates/bounds, timestamp, stored counts and partial/complete pagination state, including entries originally fetched by the beekeeper Web. History reads MUST NOT call Saturn, expose raw response JSON or treat viewport-index completeness as geographic/treatment completeness. Source revisions remain visible and separate. These are server-side cache diagnostics, not a new user-specific log or a public authenticated API.

**SRC-R34 acceptance:** With one page saved, Web shows field-center markers after a debounced read-only cache lookup on selection or an explicit load and clears them on filter changes; repeated cache inspection produces zero provider requests. A year-long date window disables provider fetching with a RU/EN explanation and offers a bounded adjustment.
