# SRC-01 — Current Research and Delivery Plan

**Normative specification:** [Source ingestion](source-ingestion.md) · **Umbrella:** [MelliAtlas MVP](../spec-umbrella-melliatlas.md) · **Checkpoint:** [STATE.json](../../STATE.json) · **Previous incremental plan:** [historical record](source-ingestion-implementation-history.md).

**Current priority (2026-11-11):** use the existing bounded `POST /backend/beemaster/planapplybees` ingestion path as the **primary candidate for full treatment records with source-linked GeoJSON**. The developer explicitly selected this direction after reviewing the third-party offline archive. Keep `/query` as the optional center-only map index and `/geojson-polygons` + `/acr` as investigative/optional detail paths; a HAR trio is **not** a prerequisite for the direct-treatment vertical slice. This is a change of implementation approach, not acceptance of the upstream filter, permission or district-coverage contract. Complete the S3c.1 gates before enabling S3c.2 or a background collector. This is an advisory plan; the developer must approve consequential implementation choices. `SRC-01` remains `READY_FOR_IMPLEMENTATION`, not accepted. Neither a successful offline test nor the existence of a local pilot verifies external source rights, district coverage or treatment geometry.

### Bounded region-agnostic pilot revision (2026-11-11)

The developer approved removing region and district defaults from the existing **viewport-index pilot**, without approving full-district ingestion. The additive migration `016_saturn_registered_regions.sql` creates an explicit registered-region table, converts the directory catalog primary key to `(source_id, subject_code)`, removes the `55` check and adds a nullable audited region code for old log compatibility. After applying migrations, run `pnpm --dir apps/api saturn:regions:seed config/saturn-demo-regions.json` to register the observed demo region; no migration automatically enables a region or contacts Saturn. The seed file can contain additional independently verified provider codes.

The shared viewport selection, both local API routes, `SaturnProvider` `/query` payload, district-directory fetch and cached district points now use the selected registered region. The directory fetch constructs a restricted **single exact URL** only after database validation. UI region/district selectors use database-backed catalogs rather than Yartsevo fallbacks. Each saved index request already includes the provider `subject` in its hashed immutable filter; district-level cross-filter lookup now also requires that `subject`. Audit and history expose the region, preserving old audit entries with `null` identity. Regression checks cover missing region, independent directory identity, no implicit network fetch and cross-region query construction. PostGIS integration is necessary to verify the additive upgrade; until it runs, this migration is unverified in a real database. Rollback disables live access while retaining cached evidence; do not drop the registration table to roll back an application deployment.

### What is actually known about the external source

- User-captured `POST /backend/beemaster/query` returns paginated **map-index** entries with `id`, `planId`, center coordinates and sometimes cadastral metadata. Multiple index entries may share one `planId`. One captured viewport reported **7,319 entries across 732 pages of 10**; that number is not a district total.
- Captured `GET /backend/beemaster/geojson-polygons` is viewport/zoom-dependent JSONP and may return clusters or points rather than usable polygons. The `/acr/{requestedId}` response contains plan dates and pesticide details, but its response `id` need not equal the URL identifier.
- A captured district directory provides names and center coordinates, **not** district borders. A captured `UpdateMap` date filter does not establish application-period or modification semantics. The 2026-11-09 user capture confirms a valid browser query **without either `UpdateMap` date field** when no date filter was selected; another captured query includes both. Only first pages have been captured, and terminal-page fixtures remain synthetic.
- Published portal user guidance documents **application-period, status, district and crop filters**, polygon-click detail, and a regional morning email digest of new/changed plans. This verifies user-facing capabilities, **not** the JSON filter contract, automatic collection rights or completeness of notifications. The separately documented authenticated Saturn SE-API is not a drop-in public Beekeeper Portal read API. See [source evidence and access status](../../../source-register.md).
- A user-supplied, third-party AI-collected July 2026 `planapplybees` archive was inspected offline on 2026-11-11. It contains **5,312 distinct field records under 274 plan IDs**, with 6,287 product associations; 166 marked revised records have effective `allPatList` contents matching `patIdsUpdate`. This supports a narrow correction to `beekeeperPlanPage.ts`: use `beeAcreage.id` for field identity, preserve `planId` separately, and select revised dates when `isUpdated` is true. The archive is **not** a byte-bound multi-endpoint browser capture, nor proof of original API response integrity, district completeness or permission. See [archive reconciliation](../../../source-register.md#offline-planapplybees-archive-reconciliation-2026-11-11).
- On 2026-11-11, a **manual live browser spot-check** retrieved three public `/acr/{fieldId}` detail bodies. Two distinct field requests (`1273662`, `1273663`) both returned plan `id: 1716288` with differing field details; a third field request (`1919940`) returned plan `id: 1798168`. These pairings also occur in the offline archive. The browser blocked a separate narrow polygon attempt before any response, and no matching-context `/query` body was captured. The offline identity diagnostic now checks ACR body ID against the indexed **plan ID** while explicitly withholding join verification. See [live evidence and limits](../../../source-register.md#bounded-live-acr-spot-check-2026-11-11-manual-public-browser).
- A follow-up public map UI session with the Smolensk/Yartsevsky filter showed sidebar fields from other regions; clicking one moved the map outside the selected district. Center coordinates in the map URL used `lat` for what appeared to be longitude and `lon` for latitude. This is a client observation, not a documented API invariant. The offline inspector now separates **three-endpoint identity candidates** (index field ID, polygon Feature ID and matching ACR body/index plan ID) from two-endpoint candidates. Synthetic tests exclude incomplete and contradictory triples; source-verified triples are still missing.
- A second bounded public map UI session reproduced the Yartsevo selection and out-of-region sidebar entries. The offline inspector additionally flags a matching-ID polygon whose coordinate bounding rectangle excludes its indexed center; containment is deliberately not treated as proof of a spatial join. No synchronized raw three-endpoint body set was captured, so S3c.1 remains blocking.
- A further pair of live public ACR responses for field IDs `2038836` and `2038837` shared body plan ID `1811436` and reproduced their centers from the older sanitized `/query` fixture exactly. The offline inspector now compares ACR centers with index centers using an explicit tolerance and marks missing/partial/different values separately. These are **non-synchronous two-endpoint observations**. The polygon endpoint yielded no response in the inspection environment, so the S3c.1 matching-geometry evidence gate remains unsatisfied.
- A subsequent **normal map UI trace** showed a visible field outline at the indexed center `(32.917616, 55.088542)` and an 11-card polygon popup whose fifth card reported plan `1811436`, the matching center and date `2026-08-09`. This supports the field-to-plan-to-displayed-geometry hypothesis for index field `2038836` and complements its earlier ACR response. It does **not** establish the polygon Feature ID, byte-exact geometry, internal click request, query time consistency or re-use permission; the [evidence register](../../../source-register.md#bounded-live-acr-spot-check-2026-11-11-manual-public-browser) records the observation and required follow-up. Do not promote an offline ID candidate to a verified geometry link on the strength of this UI trace alone.

**Throughput warning:** at the currently implemented 20-second minimum source-wide gap, 732 sequential index pages alone require at least about **4 hours 4 minutes**, before failures or per-record details. Re-evaluate the expected request count, source limits and feasible coverage before selecting any full-district strategy. Do not treat a locally chosen gap as provider-approved polling cadence.

## 2. S3c.1 — Direct full-treatment contract and bounded vertical slice (blocking)

**Objective:** verify that a single `/planapplybees` page yields source-linked field identity, plan identity, treatment dates, products and actual GeoJSON without a fragile map-index/JSONP/ACR join. The supplied third-party offline archive documents this **candidate** behavior but lacks authenticated original HTTP receipts and proof of permitted automated reuse.

**Stage A — Completed in this handoff: nested filter composition.**

1. `packages/contracts/src/index.ts`: allow a bounded JSON object under the already configured `regionContainer` in `request.parameters`, but forbid any caller-supplied `regionParameter` inside it. Continue rejecting direct region overrides and unsafe JSON parameter shapes.
2. `apps/api/src/modules/sources/providerConfiguration.ts`: merge those subordinate filters with the independently validated region code. Preserve the generic request builder, POST/GET compatibility, endpoint validation and configured source revision semantics.
3. `apps/api/test/providerConfiguration.test.ts`: assert the real documented payload shape with `district` and both `UpdateMap` dates alongside `subject`; reject attempts to replace the region or provide non-object filter containers. This is offline contract testing, **not** a live source-acceptance test.
4. Document the operator JSON configuration. Do not migrate source settings, reset previously customized providers, change the default seed, alter the 20-second shared throttle or start an unattended job.

**Stage B — Next: bounded live contract verification, requiring an approved access context.**

1. Confirm the exact permitted `/planapplybees` method, request body, nested `beekeperSearchFilter` keys (`subject`, `district`, `startDateUpdateMap`, `endDateUpdateMap`), `sortColumn`/`sortDirection`, zero-based pagination and content-size limits against a _small_ original response. The expected date serialization from the archive is ISO-8601 UTC with milliseconds; treat interval-overlap semantics, inclusion boundaries and revision/cancellation behavior as provisional until compared with controlled examples.
2. Use at most one operator-initiated page per action. Keep `pageSize <= 100`, `maxResponseBytes=2,000,000`, restricted HTTPS/DNS/redirect/MIME checks, shared source-wide throttle and current access review; a third-party script's 500/1000-page size and 0.5-second cadence do not override our policies.
3. Compare `content[].beeAcreage.id`, `planId`, `geo`, `planDate*`, `isUpdated` and `allPatList` to the existing parser with a **sanitized fixture**. Record request context, page totals and exact body hash without committing raw farm names/cadastre. Check at least one first page and an independently permitted terminal page; do not infer completion from an isolated first page.
4. Verify that `district` and period really narrow the result set; an apparently successful HTTP response that silently ignores a filter is a failure. Confirm district IDs from the provider directory and region IDs from the registered region lookup. Stop on ambiguous filtering, count drift or unexpected page content.
5. Research the publisher's current access and redistribution terms; public readability alone is not automatic permission. Document the allowed request budget and failure behavior. An authorization blocker keeps this stage in fixture-only mode.

**Offline safety increment (2026-11-11, after Stage A):** `beekeeperPlanPage.ts` now parses optional Spring pagination metadata and rejects disagreeing root/`pageable` values. `TreatmentIngestionService` validates the returned page number, size, record count and available terminal/total metadata before storing evidence or advancing its cursor; a repeated first page cannot silently count as the requested second page when provider metadata is supplied. Unit regressions and a real-PostGIS regression are included. The supplied third-party July archive contains individual full-geometry records but not authenticated page-level HTTP envelopes. A direct live request was attempted from the authoring environment but blocked at DNS resolution; upstream paging/filter semantics and reuse rights remain **unverified**. This safety work does not complete Stage B or enable automatic district ingestion.

**Stage C — Then: one limited PostGIS end-to-end treatment slice.**

1. `beekeeperPlanPage.ts` must retain distinct **field ID** and **plan ID**, revised dates when explicitly selected by `isUpdated`, and the source-selected `allPatList`. Missing claims stay unknown. Do not synthesize a polygon from a center, cadastral lookup or `/query` record.
2. `TreatmentIngestionService.syncOnePage` should ingest a verified direct page through existing restricted transport, immutable `source_documents`, pending `source_observations` and PostGIS geometry checks. Failed geometry remains attributed text-only evidence. Use the current review/publication rules; never equate a published plan with an actual completed pesticide application.
3. Add independent real-PostGIS checks for repeated `planId` across multiple field IDs, malformed geometry, duplicate page/replay, changed source revisions, restarted cursors, stable page totals, disabled source, throttling and failure before commit. Preserve historical evidence and review decisions. No schema migration is needed solely for request-filter composition; consider an additive migration only if verified snapshot/district generation identity requires it.
4. Confirm the result in local Admin preview, then in the existing map projection with explicit provenance, dates and pending/verified status. Ordinary map GETs must remain database-only, and a missing field or failed source request must not be interpreted as safe conditions.

**S3c.1 completion gate:** developer-reviewed source permissions, a reproducible small real request/response, proven provider district/time filters and pagination, and at least one correctly sourced PostGIS treatment geometry. Otherwise the direct ingestion remains a **bounded candidate** and no full district freshness is claimed. The previously built offline HAR/JSONP diagnostics remain optional tools, not blockers or preferred production collection machinery.

### Web/Admin boundary revision (2026-11-12; developer-selected)

**Stage objective:** make the beekeeper map a read-only consumer of saved PostGIS polygons and territory navigation. This revises SRC-R33/R34/R35, without establishing canonical administrative boundaries or enabling full district refresh.

**Verified owners:** `apps/web/src/{App.tsx,api/client.ts}`, `apps/web/src/components/MapCanvas.tsx`, `apps/admin/src/components/{CollectionPanel,ViewportCollectionPanel}.tsx`, `apps/api/src/{app,server}.ts`, `apps/api/src/modules/sources/providers/saturn/saturnViewportOperatorRoutes.ts`, and `packages/contracts/src/index.ts`. New `TerritorySelector.tsx` and `territoryDirectory.ts` provide a narrow read-only adapter over the registered source directory. The obsolete client viewport collection route is deleted.

**Steps and contracts:** (1) publish validated region/district navigation DTOs and GET endpoints that cannot fetch externally; (2) replace Web pilot controls with a region/district selector that centers the map, retains existing PostGIS bbox retrieval and shows empty/error states; (3) keep explicit directory refresh and both one-page `/query` diagnostics and `/planapplybees` treatment import in Admin only; (4) update RU/EN help, component/backend/E2E tests and feature cross-reference. The district center is a navigation hint, not an official administrative boundary or polygon filter. Region registration remains an explicit operator seed; no schema migration or automatic provider fetch is introduced.

**Rejected alternative:** creating an immediate multi-provider administrative-boundary registry would require authoritative geometry, stable canonical IDs, cross-provider mappings and migrations; defer it. Renaming source-specific browser paths without changing the server boundary would not solve coupling.

**Failure/recovery and acceptance:** empty registered regions show setup guidance; missing district catalogs direct the operator to an explicit refresh; API failures are distinct; obsolete async responses cannot change the selected district. Public POST source-fetch actions return 404; Admin actions remain gated, logged and throttled. Already stored evidence and review decisions remain unchanged, and the map never interprets missing observations as safety. Cover with route/component/browser tests plus existing real-PostGIS projection tests. Maintain a separate S3c.1 source-contract and access verification gate.

## 3. Architecture choices and trade-offs

| Decision                  | Selected/provisional approach                                                                                                                  | Alternative and risk to review                                                                                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D1: coverage**          | **District-scoped listing**, consistent with normative SRC-R26–R31, once the upstream `district` filter is verified.                           | A bounded viewport/interest area is only a diagnostic alternative, not complete district coverage.                                                      |
| **D2: repeat collection** | Initially full paginated generations, retaining the last successful evidence; no assumption of `updatedSince`.                                 | Delta polling can reduce calls but requires verified change and cancellation semantics and stable identity.                                             |
| **D3: complete records**  | **Direct `/planapplybees` with `beeAcreage.geo` and `allPatList`**, subject to controlled live verification; **developer-selected direction**. | `/query` + JSONP + `/acr` is many-to-one, zoom-dependent and operationally costly; use it only when a direct record is insufficient or for diagnostics. |
| **D4: trigger**           | Restricted local operator explicit one-page ingestion.                                                                                         | A public trigger requires real authorization, abuse controls and a separately approved design.                                                          |
| **D5: storage**           | Reuse the existing immutable treatment evidence and reviewed PostGIS observations; keep the map-index cache separate.                          | For S3c.2, a generation/coverage model may need a new additive migration; do not label one-page completion as fresh district coverage.                  |

**Operational/capacity decision:** first measure actual compressed/uncompressed page size and per-page time under the existing 20-second shared throttle. For a district with `N` records and page size `P <= 100`, estimate at least `ceil(N/P)` requests per complete snapshot, plus any deliberately approved enrichment. No extra ACR/PAT/JSONP requests are necessary when `/planapplybees` has all required attributes. Refuse unsupported or ambiguous filters, record count drift, retain raw evidence and keep partial runs visibly partial. Do not add a queue, new persistence engine, generic plugin runtime or parallel source fetches without measured need.

## 4. Implementation order, recovery and acceptance evidence

- **Immediate code owners:** `packages/contracts/src/index.ts`, `apps/api/src/modules/sources/providerConfiguration.ts`, and `apps/api/test/providerConfiguration.test.ts` for nested request composition. The operator form already edits the bounded `parameters` JSON; no new UI shape is needed in Stage A. Maintain the cross-module contract in `packages/contracts/contract.md` and the source-module contract.
- **Stage B owners:** `apps/api/config/providers/fgis-saturn.json` is an inert demo preset, not permission; `docs/source-register.md` records original evidence and open questions. Use `provider:seed` only on an operator-approved instance, preserving custom settings. Runtime source access must still be reviewed and enabled by the documented policy.
- **Stage C owners:** `apps/api/src/modules/sources/{beekeeperPlanPage,treatmentIngestion,treatmentMapProjection}.ts` and their API/real-PostGIS tests. Integrate through existing `TreatmentIngestionService` rather than introducing a second fetcher. Preserve separate immutable source-page and observation identity; do not rewrite old source documents or migrate old plan-keyed identities speculatively.
- **Failure/recovery:** invalid filters are rejected before any request; source failures leave saved evidence untouched, and the current DB cursor does not advance. A concurrent worker must be rejected by the DB lock; configuration revision conflicts block commit. A failed/partial scan must not overwrite an earlier verified treatment or set a fresh district TTL. Operator-only retries honor throttle and may return zero newly stored observations for already imported evidence.
- **Independent acceptance:** offline request composition tests for nested filter values and region override, then authorized fixture-to-ingestion and PostGIS restart/pagination/geometry tests. Separate the measured live provider contract from deterministic automated tests; record what was and was not executed. Full `run-tests.sh` (including DB and browser prerequisites) is the external handoff gate.

## 5. S3c.2 — District coverage and TTL (conditional following stage)

Implement only after verified district/filter/boundary contracts and a developer-approved D1–D5 design. `SRC-R26`–`SRC-R31` in the normative specification own the required 24-hour coverage semantics; a 24-hour local TTL is **not** proof that the provider is up to date.

1. **Collection identity and generations.** If full refresh is selected, add a distinct collection-generation ID for each actual filter/scope and store an immutable page-to-generation relationship. Current migration 014 uses only `(source_id, source_revision, request_hash)` and deliberately cannot refetch a completed key; do not reuse that key as the generation ID. Proposed additive migration and owner methods must specify uniqueness, active-snapshot promotion, retention and revision invalidation before implementation.
2. **Bounded orchestration.** A proposed `apps/api/src/modules/sources/districtCollection.ts` may coordinate the existing `districtCacheRepository.ts`, `districtCacheState.ts` and provider adapter. Each attempt must reserve the common source-wide request gate, claim a single matching job, commit one validated page and its checkpoint atomically, and resume an incomplete generation after crash. Do not treat `viewport_index_complete` as district completeness. Do not revive `regionalCollection.ts` or the old `REGION_SCAN_DAILY_UTC_HOUR` schedule.
3. **Coverage projection.** Distinguish `fresh`, `stale`, `partial`, `unknown` and `failed`, with exact source/filter/time context. Mark `fresh` only after a complete permitted listing and boundary/window verification. Retain the last successful generation through a failed replacement. A successful zero-row listing is meaningful only within the verified query scope. Crossing an unknown neighboring district boundary remains potentially incomplete.
4. **Read and UI path.** Ordinary `/api/v1/notices` reads remain PostGIS-only. If the spec-approved backend demand trigger is used, enqueue/coalesce it asynchronously; never fan out on map pan or block a map response. Admin `CollectionPanel.tsx` and related contracts show progress, last complete time, counts and sanitized failures; manual refresh bypasses TTL but **not** source throttling or access restrictions.
5. **Capacity and retention.** Before implementation, benchmark a bounded real/synthetic page set, estimate worst-case number of index/detail/polygon calls, time to completion, PostGIS volume and retained generations. Confirm the expected workload is compatible with source limits; otherwise return the D1 collection scope for developer reconsideration.

**Transaction sketch:** claim one key/generation; reserve global slot before each permitted external attempt; fetch/validate one page; atomically save evidence and advance the generation cursor; after a verified terminal page, atomically mark the generation complete and promote its projection. On timeout, crash, changing upstream pagination or source-revision conflict, keep the previous completed generation available with an explicit stale/partial indicator. Never convert a failed partial scan into a zero-result fresh cache.

**Independent acceptance:** real PostGIS migration/restart tests, duplicate concurrent requests, identical and different districts, throttle across endpoints, stable page totals and deliberate count drift, changed config, 23h59m/24h TTL boundaries, failed replacement, zero-result completion, border-crossing incompleteness and desktop/mobile display. Provider access is separately reviewed. No broker, external scheduler, new public authentication design or mailbox automation is authorized by this plan alone.

## 6. Verification and developer gates

Before any source change, resolve verified current file owners and tests, then run the relevant focused checks. Canonical local checks (with dependencies installed) are:

```bash
python3 -B tools/specs/validate_state.py
pnpm format:check
pnpm typecheck
pnpm test
pnpm build
pnpm --dir apps/api test:db
pnpm e2e
```

`test:db` requires isolated PostgreSQL/PostGIS; Playwright uses deterministic intercepted provider/API responses. Record executed checks and omissions; green synthetic tests cannot certify live source behavior, geometry identity, rights or developer acceptance. The canonical read-only `run-tests.sh` is the final integration gate in an appropriately prepared developer environment; formatting belongs to `run-format.sh` beforehand.

**Required review checkpoints:** (1) developer approval of the existing or materially revised normative requirements; (2) S3c.1 source evidence and D1–D5 architectural choices; (3) vertical-slice acceptance with actual provenance; (4) S3c.2 coverage/TTL acceptance. `STATE.json` and archive transitions remain developer-controlled. The optional official email feasibility work in `SRC-R32` is a separate research decision, not permission to implement mailbox ingestion.
