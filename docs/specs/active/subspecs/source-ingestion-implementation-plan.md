# SRC-01 — Current Research and Delivery Plan

**Normative specification:** [Source ingestion](source-ingestion.md) · **Umbrella:** [MelliAtlas MVP](../spec-umbrella-melliatlas.md) · **Checkpoint:** [STATE.json](../../STATE.json) · **Previous incremental plan:** [historical record](source-ingestion-implementation-history.md).

**Current priority (2026-11-11):** complete the S3c.1 evidence and architecture-decision gate before implementing S3c.2 district coverage and 24-hour TTL. The bounded legacy `planapplybees` parser correction preserves field-level IDs and revised dates; it does not approve or implement a district collector. This is an advisory plan; the developer must approve consequential implementation choices. `SRC-01` remains `READY_FOR_IMPLEMENTATION`, not accepted. Neither a successful offline test nor the existence of a local pilot verifies external source rights, district coverage or treatment geometry.

### Bounded region-agnostic pilot revision (2026-11-11)

The developer approved removing region and district defaults from the existing **viewport-index pilot**, without approving full-district ingestion. The additive migration `016_saturn_registered_regions.sql` creates an explicit registered-region table, converts the directory catalog primary key to `(source_id, subject_code)`, removes the `55` check and adds a nullable audited region code for old log compatibility. After applying migrations, run `pnpm --dir apps/api saturn:regions:seed config/saturn-demo-regions.json` to register the observed demo region; no migration automatically enables a region or contacts Saturn. The seed file can contain additional independently verified provider codes.

The shared viewport selection, both local API routes, `SaturnProvider` `/query` payload, district-directory fetch and cached district points now use the selected registered region. The directory fetch constructs a restricted **single exact URL** only after database validation. UI region/district selectors use database-backed catalogs rather than Yartsevo fallbacks. Each saved index request already includes the provider `subject` in its hashed immutable filter; district-level cross-filter lookup now also requires that `subject`. Audit and history expose the region, preserving old audit entries with `null` identity. Regression checks cover missing region, independent directory identity, no implicit network fetch and cross-region query construction. PostGIS integration is necessary to verify the additive upgrade; until it runs, this migration is unverified in a real database. Rollback disables live access while retaining cached evidence; do not drop the registration table to roll back an application deployment.

### What is actually known about the external source

- User-captured `POST /backend/beemaster/query` returns paginated **map-index** entries with `id`, `planId`, center coordinates and sometimes cadastral metadata. Multiple index entries may share one `planId`. One captured viewport reported **7,319 entries across 732 pages of 10**; that number is not a district total.
- Captured `GET /backend/beemaster/geojson-polygons` is viewport/zoom-dependent JSONP and may return clusters or points rather than usable polygons. The `/acr/{requestedId}` response contains plan dates and pesticide details, but its response `id` need not equal the URL identifier.
- A captured district directory provides names and center coordinates, **not** district borders. A captured `UpdateMap` date filter does not establish application-period or modification semantics. The 2026-11-09 user capture confirms a valid browser query **without either `UpdateMap` date field** when no date filter was selected; another captured query includes both. Only first pages have been captured, and terminal-page fixtures remain synthetic.
- Published portal user guidance documents **application-period, status, district and crop filters**, polygon-click detail, and a regional morning email digest of new/changed plans. This verifies user-facing capabilities, **not** the JSON filter contract, automatic collection rights or completeness of notifications. The separately documented authenticated Saturn SE-API is not a drop-in public Beekeeper Portal read API. See [source evidence and access status](../../../source-register.md).
- A user-supplied, third-party AI-collected July 2026 `planapplybees` archive was inspected offline on 2026-11-11. It contains **5,312 distinct field records under 274 plan IDs**, with 6,287 product associations; 166 marked revised records have effective `allPatList` contents matching `patIdsUpdate`. This supports a narrow correction to `beekeeperPlanPage.ts`: use `beeAcreage.id` for field identity, preserve `planId` separately, and select revised dates when `isUpdated` is true. The archive is **not** a byte-bound multi-endpoint browser capture, nor proof of original API response integrity, district completeness or permission. See [archive reconciliation](../../../source-register.md#offline-planapplybees-archive-reconciliation-2026-11-11).
- On 2026-11-11, a **manual live browser spot-check** retrieved three public `/acr/{fieldId}` detail bodies. Two distinct field requests (`1273662`, `1273663`) both returned plan `id: 1716288` with differing field details; a third field request (`1919940`) returned plan `id: 1798168`. These pairings also occur in the offline archive. The browser blocked a separate narrow polygon attempt before any response, and no matching-context `/query` body was captured. The offline identity diagnostic now checks ACR body ID against the indexed **plan ID** while explicitly withholding join verification. See [live evidence and limits](../../../source-register.md#bounded-live-acr-spot-check-2026-11-11-manual-public-browser).
- A follow-up public map UI session with the Smolensk/Yartsevsky filter showed sidebar fields from other regions; clicking one moved the map outside the selected district. Center coordinates in the map URL used `lat` for what appeared to be longitude and `lon` for latitude. This is a client observation, not a documented API invariant. The offline inspector now separates **three-endpoint identity candidates** (index field ID, polygon Feature ID and matching ACR body/index plan ID) from two-endpoint candidates. Synthetic tests exclude incomplete and contradictory triples; source-verified triples are still missing.
- A second bounded public map UI session reproduced the Yartsevo selection and out-of-region sidebar entries. The offline inspector additionally flags a matching-ID polygon whose coordinate bounding rectangle excludes its indexed center; containment is deliberately not treated as proof of a spatial join. No synchronized raw three-endpoint body set was captured, so S3c.1 remains blocking.
- A further pair of live public ACR responses for field IDs `2038836` and `2038837` shared body plan ID `1811436` and reproduced their centers from the older sanitized `/query` fixture exactly. The offline inspector now compares ACR centers with index centers using an explicit tolerance and marks missing/partial/different values separately. These are **non-synchronous two-endpoint observations**. The polygon endpoint yielded no response in the inspection environment, so the S3c.1 matching-geometry evidence gate remains unsatisfied.
- A subsequent **normal map UI trace** showed a visible field outline at the indexed center `(32.917616, 55.088542)` and an 11-card polygon popup whose fifth card reported plan `1811436`, the matching center and date `2026-08-09`. This supports the field-to-plan-to-displayed-geometry hypothesis for index field `2038836` and complements its earlier ACR response. It does **not** establish the polygon Feature ID, byte-exact geometry, internal click request, query time consistency or re-use permission; the [evidence register](../../../source-register.md#bounded-live-acr-spot-check-2026-11-11-manual-public-browser) records the observation and required follow-up. Do not promote an offline ID candidate to a verified geometry link on the strength of this UI trace alone.

**Throughput warning:** at the currently implemented 20-second minimum source-wide gap, 732 sequential index pages alone require at least about **4 hours 4 minutes**, before failures or per-record details. Re-evaluate the expected request count, source limits and feasible coverage before selecting any full-district strategy. Do not treat a locally chosen gap as provider-approved polling cadence.

## 2. S3c.1 — Research and contract verification (blocking)

**Objective:** establish which source records, filters, time ranges, geometries and usage rights can support one accurate, repeatable beekeeper-facing treatment observation. Research and developer review precede a production collector.

1. **Reconcile the evidence register.** Inspect the official portal user guidance, recorded browser captures, current source terms and `apps/api/config/providers/fgis-saturn.json`. Classify every claim as observed, documented, inferred or unknown. Verify the currently configured host and paths from a permitted environment; do not automatically contact undocumented endpoints or increase the source allowlist.
2. **Obtain matching-context captures with permission.** Record UTC capture times, subject/district, exact bbox/zoom, visible UI filters and bounded response bodies for `/query`, `/geojson-polygons` and clicked `/acr/{id}`. Prioritize **field `2038836` / plan `1811436`** because the map UI now provides a visible polygon-to-plan trace at its previously captured center. Use browser Network export from an authorized normal portal session, not a workaround for the current browser's blocked direct polygon request. Preserve the exact polygon request URL and JSONP response alongside the matching viewport index page and clicked ACR body. The local `saturnCaptureCli.ts --har-preview <capture.har> --acr-id 2038836` command first provides an offline, non-disclosing endpoint-count/readability inventory. Its `--har <capture.har> --acr-id 2038836` mode then validates a **single** complete HAR trio offline, reusing the same body parsers and manifest checks without writing raw bodies; it rejects sessions with multiple matching endpoint requests instead of silently selecting them. A preview candidate does not imply a valid full inspection. Use the existing separate-file and optional integrity-manifest flow for direct body captures. Keep complete HAR files private because they may contain credentials and unrelated sensitive data. Include several distinct field IDs, repeated plan IDs and different geometries; keep raw names, cadastral details and private data out of public fixtures. An overlapping request area or a matching UI card is not a proven Feature ID join.
3. **Verify identity and geometry.** Determine whether a specific index feature ID corresponds to a clicked map Feature ID and `/acr` lookup; keep the returned body ID separate. The offline ACR inspector now reports only structural date/product counts and anomalies; it does not establish treatment identity or validate application-date semantics. Examine clustering at suitable zoom levels and test repeated coordinates/cadastral numbers. Do not join by center proximity, `planId`, a polygon hash or a matching ID alone without contextual evidence. Document at least one complete trace from list entry to credible geometry and treatment details, or state precisely why the trace is not possible.
   **Completed narrow regressions:** the legacy `planapplybees` parser and persistence attributes distinguish field ID from `planId` and use explicitly marked revised dates; offline tests cover shared plans and missing revisions. The offline cross-endpoint inspector additionally compares requested field IDs with indexed plan IDs and reported ACR body plan IDs, and identifies **candidate triples** only when an index field ID, polygon Feature ID, and ACR body plan ID align. Its tests use synthetic geometry and preserve separate field identities. The manual live ACR spot-check supports the field/plan distinction but **does not resolve** the separate `/query` → polygon → `/acr` join or repair already stored plan-keyed observations. Next obtain a matching-context polygon capture and one `/query` page for a common field ID, with request metadata; otherwise keep the S3c.1 gate open. Any historical backfill must preserve the original captured bodies and review decisions rather than rewriting published evidence in place.
4. **Verify filters and pagination.** Compare portal selection with request payloads for application period, `UpdateMap` interval, district and bbox. Verify inclusive/exclusive boundaries, timezone and cancel/change behavior. Collect a permitted bounded terminal-page sequence and compare ordering/counts across repeated reads; account for additions/removals during pagination. Stop rather than infer `updatedSince`, spatial completeness or a stable snapshot contract.
5. **Verify access and capacity.** Record publisher terms, permitted automatic access/reuse, actual throttling behavior and an explicit per-operation request budget. Consider the official subscribed email as a **candidate change signal** only after obtaining an authentic redacted `.eml` and verifying IDs, revisions, delivery and rights. Never put mailbox credentials or untrusted email links into collection logic at this stage.
6. **Present research conclusions for developer review.** Update `docs/source-register.md` with provenance, reproducible request/response descriptions, contradictions and explicit unknowns. Compare the architectural alternatives in Section 3, request decisions on material trade-offs, and revise this plan as necessary. A material change to the user-facing SRC requirements requires normative spec approval; the plan alone cannot change them.

**Gate:** the developer has reviewed the evidence and chosen a viable collection scope. The actual filter meaning, stable identity, geometry association, legal/operational access and bounded page termination are established for that scope. Otherwise remain in research mode and expose only clearly labelled cached index centers; do not claim a verified district refresh.

## 3. Architectural alternatives — decisions pending

The following are **options, not implementation approvals**. Record the developer's selection and rationale here after the evidence gate; do not convert the first plausible design into an irreversible schema.

| Decision                           | Viable alternatives                                                                                                                                        | Trade-off / provisional recommendation                                                                                                                                                                                                                                  |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D1: spatial collection scope**   | A: complete administrative district; B: bounded beekeeper interest area; C: interest area first, district coverage later                                   | **A is the current normative S3c scope.** B/C are research alternatives only and require an approved specification revision before replacing district collection. They cannot claim district completeness; first measure borders, pagination and request budgets for A. |
| **D2: repeat collection**          | A: immutable full collection generations; B: incremental changes from a verified upstream change filter; C: hybrid initial snapshot + verified deltas      | **A is safer initially if a bounded snapshot is practical**; B/C may reduce traffic only if updates, deletions and stable IDs are proven. Explicitly account for an incomplete replacement generation.                                                                  |
| **D3: record enrichment**          | A: fetch every `/acr` detail and associated polygon; B: fetch details only for selected/high-interest index entries; C: supported official bulk/export API | **B can support an explicitly partial diagnostic or pilot**, not acceptance of full treatment coverage. Verify whether A or C is feasible under the district requirement; revise the normative spec if changing promised scope.                                         |
| **D4: user-triggered collection**  | A: local operator only; B: locally enabled explicit beekeeper pilot; C: authenticated public request queued server-side                                    | Keep B restricted to the existing local pilot. Production C needs a separate identity/abuse-control design; ordinary map GET must remain database-only.                                                                                                                 |
| **D5: state and evidence storage** | A: existing immutable viewport index plus a generation layer; B: independent normalized observations with references to capture generations                | Keep index and treatment observations **semantically separate**. Choose the smallest persistent generation/projection design that supports the verified D1–D3 workflow; avoid copying raw payloads into every table.                                                    |

**Decision evidence expected:** one small comparison of candidate complexity, request count/cadence, operational cost, data quality, failure recovery, schema evolution and tests. Research established libraries and cross-language implementations where useful, but introduce Rust, a queue, microservices or another database only after measured need. Routine local implementation details do not require an option matrix.

## 4. Next bounded vertical slice — proposed after S3c.1 approval

**Outcome:** show one source-backed treatment with verified relationship between its identity, dates, pesticide attributes and geometry in a small approved pilot area. Reuse existing public `GET /api/v1/notices` only if the resulting observation meets its validation and review-status policy. Do not replace previously imported treatment polygons with map-index points.

1. **Provider adapter:** extend `apps/api/src/modules/sources/providers/saturn/` with only the verified detail/geometry parsing and a bounded retrieval method. Reuse `SaturnProvider`, `SaturnViewportPageFetcher`, `RestrictedSourceFetcher`, the source-wide throttle and audited request lifecycle. Proposed new files are provisional until D1–D3 are selected; avoid creating a second general fetcher or generic source framework.
2. **Domain identity:** document the relationships among `featureId`, `planId`, cadastral number, requested ACR ID, returned ACR ID, source document version and observed treatment. Define distinct identity, update and conflict rules for a plan affecting several parcels. Keep uncertain matches as candidates, never silently merge or publish them.
3. **Persistence:** retain immutable captured evidence and reference it from normalized records. Use `treatmentIngestion.ts` and `treatmentMapProjection.ts` where their contracts genuinely apply. Introduce only an additive migration (next number after `016`) when the selected model cannot be represented safely using current schema; verify upgrade from 016 and fresh initialization. Do not modify migrations 001–016.
4. **API and UI:** change `packages/contracts` and the API/Web modules only if the approved vertical slice needs new fields. Show explicit source, timestamps, review status, geometry precision and absence-of-coverage warnings. Keep the local admin source controls separate from the beekeeper map and do not infer pesticide danger/safety from a marker.
5. **Failure/recovery:** retain old published observations on provider failure, distinguish malformed index/detail/polygon from no result, preserve a failed capture trace and permit operator-only retry after throttle. An unresolved ID association must not update a verified observation. A disabled source stops external calls without erasing historical evidence.

**Independent tests:** captured-contract parsers, ID collisions and repeated `planId`, different ACR URL/body IDs, missing or invalid geometry, mixed/null detail fields, contradictory dates, duplicate/revised records, source disabled/revoked, malformed responses and rate caps. Use a real isolated PostGIS schema to verify idempotent linkage and restart behavior; use Web/Admin component and Playwright tests for accurate attribution and unverified states. An authorized limited live pilot is separate evidence, never part of automated tests.

**Completion gate:** a documented trace from permitted source captures to one displayed observation, independently checked against the portal and reviewed by the developer. If a complete join cannot be established, deliver an index-only diagnostic with the limitation visible and revisit D1–D3 rather than forcing approximate geometry into the treatment model.

## 5. S3c.2 — District coverage and TTL (conditional following stage)

Implement only after verified district/filter/boundary contracts and a developer-approved D1–D5 design. `SRC-R26`–`SRC-R31` in the normative specification own the required 24-hour coverage semantics; a 24-hour local TTL is **not** proof that the provider is up to date.

1. **Collection identity and generations.** If full refresh is selected, add a distinct collection-generation ID for each actual filter/scope and store an immutable page-to-generation relationship. Current migration 014 uses only `(source_id, source_revision, request_hash)` and deliberately cannot refetch a completed key; do not reuse that key as the generation ID. Proposed additive migration and owner methods must specify uniqueness, active-snapshot promotion, retention and revision invalidation before implementation.
2. **Bounded orchestration.** A proposed `apps/api/src/modules/sources/districtCollection.ts` may coordinate the existing `districtCacheRepository.ts`, `districtCacheState.ts` and provider adapter. Each attempt must reserve the common source-wide request gate, claim a single matching job, commit one validated page and its checkpoint atomically, and resume an incomplete generation after crash. Do not treat `viewport_index_complete` as district completeness. Do not revive `regionalCollection.ts` or the old `REGION_SCAN_DAILY_UTC_HOUR` schedule.
3. **Coverage projection.** Distinguish `fresh`, `stale`, `partial`, `unknown` and `failed`, with exact source/filter/time context. Mark `fresh` only after a complete permitted listing and boundary/window verification. Retain the last successful generation through a failed replacement. A successful zero-row listing is meaningful only within the verified query scope. Crossing an unknown neighboring district boundary remains potentially incomplete.
4. **Read and UI path.** Ordinary `/api/v1/notices` reads remain PostGIS-only. If the spec-approved backend demand trigger is used, enqueue/coalesce it asynchronously; never fan out on map pan or block a map response. Admin `CollectionPanel.tsx` and related contracts show progress, last complete time, counts and sanitized failures; manual refresh bypasses TTL but **not** source throttling or access restrictions.
5. **Capacity and retention.** Before implementation, benchmark a bounded real/synthetic page set, estimate worst-case number of index/detail/polygon calls, time to completion, PostGIS volume and retained generations. Confirm the expected workload is compatible with source limits; otherwise return the D1 collection scope for developer reconsideration.

**Transaction sketch:** claim one key/generation; reserve global slot before each permitted external attempt; fetch/validate one page; atomically save evidence and advance the generation cursor; after a verified terminal page, atomically mark the generation complete and promote its projection. On timeout, crash, changing upstream pagination or source-revision conflict, keep the previous completed generation available with an explicit stale/partial indicator. Never convert a failed partial scan into a zero-result fresh cache.

**Independent acceptance:** real PostGIS migration/restart tests, duplicate concurrent requests, identical and different districts, throttle across endpoints, stable page totals and deliberate count drift, changed config, 23h59m/24h TTL boundaries, failed replacement, zero-result completion, border-crossing incompleteness and desktop/mobile display. Provider access is separately reviewed. No broker, external scheduler, new public authentication design or mailbox automation is authorized by this plan alone.

## 6. Verification and developer gates

Before any source change, resolve verified current file owners and tests, then run the relevant focused checks. Canonical local checks (with dependencies installed) are:

```bash
python3 -B tools/specs/validate_state.py
pnpm format:check
pnpm typecheck
pnpm test
pnpm build
pnpm --dir apps/api test:db
pnpm e2e
```

`test:db` requires isolated PostgreSQL/PostGIS; Playwright uses deterministic intercepted provider/API responses. Record executed checks and omissions; green synthetic tests cannot certify live source behavior, geometry identity, rights or developer acceptance. The canonical read-only `run-tests.sh` is the final integration gate in an appropriately prepared developer environment; formatting belongs to `run-format.sh` beforehand.

**Required review checkpoints:** (1) developer approval of the existing or materially revised normative requirements; (2) S3c.1 source evidence and D1–D5 architectural choices; (3) vertical-slice acceptance with actual provenance; (4) S3c.2 coverage/TTL acceptance. `STATE.json` and archive transitions remain developer-controlled. The optional official email feasibility work in `SRC-R32` is a separate research decision, not permission to implement mailbox ingestion.
